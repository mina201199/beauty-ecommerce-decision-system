# 專題規格書

> 電商轉換漏斗診斷與流失預警系統
> 最後更新：2026-08-06

---

## 1. 專案定位

**一句話**
> 用一家美妝電商 2000 萬筆真實用戶行為資料，定位轉換流程的漏水點，並建立 session 層級的流失預警模型，把「哪裡在漏、漏多少錢、該怎麼補」量化成營運可執行的決策。

**這不是行銷專案，是營運流程優化專案。**
面試時的定位是「營運分析／需求規劃」，不是「行銷企劃」。所有產出的語言都要對齊這一點：講的是**流程效率與損失量化**，不是「檔期建議」。

**求職對應職缺**
`E-commerce Operations Analyst`、`Business Analyst`、`Supply Chain / Demand Analyst`、`BI Analyst`、`Product Analyst`

---

## 2. 商業問題

一家中型美妝電商，5 個月內有 2000 萬次用戶互動，但絕大多數瀏覽沒有變成訂單。營運端需要知道：

| # | 問題 | 對應模組 |
|---|---|---|
| Q1 | 用戶從瀏覽到購買，**在哪一段流失最嚴重**？ | 模組 1 |
| Q2 | 加入購物車後又移除的行為，**集中在哪些品牌與價格帶**？ | 模組 1 |
| Q3 | 能不能在用戶還在站上時，**即時判斷他會不會買**？ | 模組 2 |
| Q4 | 如果照模型建議去做，**一年能多賺多少錢**？ | 模組 3 |
| Q5 | 折扣不划算的話，**還有什麼不花錢的解方**？ | 模組 4 |

Q4 是整份專題的收斂點，Q5 是它的延伸。

---

## 3. 資料

**來源**：[eCommerce Events History in Cosmetics Shop](https://www.kaggle.com/datasets/mkechinov/ecommerce-events-history-in-cosmetics-shop)
由 REES46 Marketing Platform / Open CDP 提供，**真實資料非合成**。使用時需標註來源。

| 項目 | 內容 |
|---|---|
| 期間 | 2019/10 – 2020/02（5 個月） |
| 規模 | 約 2000 萬筆事件、5 個 CSV、約 450MB |
| 粒度 | 一列 = 一個用戶對一個商品的一次動作 |

**欄位**

| 欄位 | 說明 |
|---|---|
| `event_time` | 事件發生時間（UTC） |
| `event_type` | `view` / `cart` / `remove_from_cart` / `purchase` |
| `product_id` | 商品 ID |
| `category_id` | 品類 ID |
| `category_code` | 品類名稱（**大量缺失**，只有主要品類才有） |
| `brand` | 品牌（小寫，**有缺失**） |
| `price` | 價格 |
| `user_id` | 用戶 ID（跨 session 固定） |
| `user_session` | Session ID（長時間未動作後會換新的） |

**資料的關鍵優勢**
一般電商公開資料只有訂單，這份有完整行為流，而且**包含 `remove_from_cart`** —— 這是罕見的「明確放棄訊號」，也是本專題最主要的差異化來源。

## 4. 四個模組

### 模組 1：轉換漏斗診斷 ★☆☆

**做什麼**
- 計算 `view → cart → purchase` 各階段轉換率
- 拆解維度：品牌、價格帶、品類、星期／時段
- 專門分析 `remove_from_cart`：**加購後放棄率**最高的是哪些商品

**產出**
- 互動式漏斗圖與 Sankey 圖（`outputs/figures/`）
- 「流失熱點 Top 20」表格（`outputs/tables/`）

**驗收標準**
能用一句話說出：「流失最嚴重的環節是 ___，集中在 ___ 品牌／___ 價格帶，佔總流失的 ___%」

**這一關的價值**：這是整個專題唯一能產生「反直覺發現」的地方，而反直覺發現就是你的面試鉤子。

---

### 模組 2：Session 購買意圖預測 ★★☆

**做什麼**
針對每個 session，用**前 3 分鐘**的行為預測「這個 session 之後會不會購買」。
觀察窗長度由實際分布掃描決定，見 4.1 節。

**特徵設計（只能用觀察窗內的資料）**

| 類別 | 特徵 |
|---|---|
| 行為量 | 瀏覽次數、加購次數、移除次數、事件總數 |
| 行為比 | 移除/加購比（**不做加購/瀏覽比** —— 74% 的加購無瀏覽記錄，該比率會讓模型學到追蹤缺陷）|
| 商品廣度 | 看過幾個不同商品、幾個品牌、幾個品類 |
| 價格 | 瀏覽商品均價、最高價、價格全距 |
| 節奏 | 事件間隔中位數與最大值、觀察窗內活躍度 |
| 時間 | 星期幾、幾點、是否假日 |

**模型**：LightGBM 二元分類。**不使用 `scale_pos_weight` 或 SMOTE** ——
合格樣本的正樣本佔 13.5%，不屬於嚴重不平衡，加權只會破壞機率校準，
而模組 3 的營收試算需要能反映真實機率的分數。

**解釋**：特徵重要度採 `gain`（非預設的 `split`）。
`split` 只數分裂次數，會嚴重偏袒連續型高基數特徵，導向相反的結論。

**驗收標準**
- PR-AUC 明顯優於 baseline（baseline = 整體購買率）
- **AUC 若超過 0.95，先假設自己洩漏了**，回去檢查特徵
- 能說出前 5 個最重要的行為訊號，並解釋為何用 gain 而非 split

---

### 模組 3：商業影響量化 ★☆☆ ← **決定專題價值的模組**

**做什麼**
把模型指標翻譯成錢：

```
若對模型判定的 Top 20% 高意圖 session 發放 10% 折扣：
  觸及 session 數        = ?
  預估額外轉換數         = 觸及數 × 基準轉換率 × 假設提升幅度
  預估增額營收           = 額外轉換數 × 平均客單價
  折扣成本               = 觸及且原本就會買的訂單 × 客單價 × 折扣率
  淨效益                 = 增額毛利 - 折扣成本
```

**必須做到的三件事**
1. **所有假設寫在 README 明處**（折扣幅度、提升幅度、毛利率都在 `src/config.py`）
2. **做敏感度分析**：假設提升幅度從 5% 到 25%，淨效益的變化範圍
3. **誠實標註這是估算不是實測**，並附上驗證用的 A/B test 設計建議

**驗收標準**
能講出一句話：「這套系統預估每年可帶來 ___ 的淨增額毛利，前提是 ___，需要一個為期 ___ 週的 A/B test 驗證。」

---

### 模組 4：膚況導向商品探索引擎 ★★☆

**為什麼有這個模組**
模組 1 指出槓桿在「瀏覽→加購」，模組 3 證明折扣挽回不划算。這個模組回答「那什麼才是解方」—— 商品探索優化作用在同一環節，但**沒有毛利成本**，損益兩平門檻趨近於零。

**做什麼**
- 同膚質評分：以兩層貝氏平滑計算「跟你同膚質的人給幾分、多少比例推薦」
- 成分安全過濾：解析 INCI 成分表，標記變性酒精、致敏香料、精油
- 需求對應：把商品分類與 highlights 對應到保濕／痘痘／暗沉／抗老等需求
- 排序對照：同膚質排序 vs 全站排序的 Top-N 重疊率

**資料**：另一份資料集（Sephora，2023），與主資料集不可串接，需在報告中明確標註邊界。

**驗收標準**
能說出「以全站評分排序時，Top 10 有 ___ 項不是該膚質族群評價最好的商品」，且該數字來自**兩種排序共用同一加權公式、只替換評分來源**的公平比較。

## 4.1 實際執行與原計畫的差異

計畫會因為看到資料而改變，這是正常的。以下每一項變更都有資料依據：

| 原計畫 | 實際執行 | 原因 |
|---|---|---|
| 觀察窗 10 分鐘 | **3 分鐘** | 10 分鐘會排除 42.55% 的購買者。掃描 1/2/3/5/10/15/30 分鐘後選定 |
| 模組 3 做 RFM 分群 | **未執行** | 與「診斷→預測→值多少錢→解方」的主線無關，優先度低於其他模組 |
| 模組 4 做加購組合推薦 | **改做膚況導向探索** | 前三個模組的結論指向「探索環節」才是槓桿，加購組合無法回答那個問題 |
| 品類維度分析 | **不列入主要結論** | `category_code` 覆蓋率僅 1.81% |
| 折扣提升幅度設為固定假設值 | **改為敏感度分析＋損益兩平點** | 該參數無法從歷史資料推得，只能靠 A/B test 實測 |

## 5. 實作順序（重要）

**不要照模組編號做。照下面的順序做。**

| 階段 | 內容 | 為什麼是這個順序 |
|---|---|---|
| **第 1 週** | 環境 → 下載 → 清洗 → **模組 1** | 先摸熟資料。沒有理解資料就建模是最常見的失敗 |
| **第 2 週** | **模組 3 的骨架**（用假數字先跑通） | **反直覺但關鍵**：先確定「錢怎麼算」，才知道模型要優化什麼 |
| **第 3–4 週** | **模組 2**（含特徵工程與防洩漏檢查） | 最花時間的一關，前面兩關會給你設計特徵的直覺 |
| **第 5 週** | 把模型實測的 lift curve 接回模組 3 | 到這裡 MVP 就完成了，已經是完整故事 |
| **第 6 週** | Streamlit 儀表板 + README | 包裝。這關決定別人願不願意看你的東西 |
| **第 7–8 週** | 模組 4 探索引擎 + demo 影片 + 發表 | 有餘力才做 |

**第 5 週結束時就該有一個可以拿去面試的完整作品。** 後面都是加分。

## 6. 防雷清單

| # | 陷阱 | 徵兆 | 對策 |
|---|---|---|---|
| 1 | **Data Leakage** | AUC > 0.95，好到不真實 | 觀察窗內已購買的 session 整個排除；purchase 事件永不進特徵。程式內建自動警報 |
| 2 | **時間穿越** | 用 `train_test_split` 隨機切分 | 必須用時間切分：10–12 月訓練、1 月驗證、2 月測試 |
| 3 | **看錯指標** | 用 accuracy 且分數很高 | 購買事件佔比極低，accuracy 毫無意義。看 **PR-AUC** |
| 4 | **記憶體爆掉** | pandas 讀檔就當掉 | 已在 `config.py` 指定 dtype，並轉存 parquet |
| 5 | **做太多做不完** | 多個模組同時開工 | 先求完整 MVP，加分模組最後再做 |
| 6 | **假設藏起來** | 直接報「年增 500 萬」 | 所有假設列在 README，附敏感度分析 |

## 8. 面試怎麼用

**30 秒版本**
> 我分析了一家美妝電商 2,069 萬筆真實行為資料。最大的漏水點在購物車 —— 87% 的加購沒有成交。
> 但我發現放棄率跟價格幾乎無關，五個價格帶只差 2.5 個百分點，所以折扣不會是解方。
> 我建了 session 層級的意圖模型，前 20% 高分涵蓋 43.9% 的購買者。用它做折扣試算後，
> 結論是 10% 折扣在合理假設下仍然虧損，要 2.34% 挽回率才打平。我的建議是折扣降到 5%，
> 或改做沒有毛利成本的商品探索優化 —— 後者的損益兩平門檻趨近於零。

**準備好被追問的三題**
1. 「你怎麼確定沒有 data leakage？」→ 講觀察窗設計與時間切分
2. 「這個增額營收數字怎麼算的？」→ 講假設、敏感度分析、合理性檢核，以及為何核心產出是損益兩平門檻而非單一預估值
3. 「如果讓你上線，你會怎麼做？」→ 講 A/B test 設計、監控指標、模型退化

**你的獨特優勢（一定要講）**
> 我做過外貿業務助理和測試業專案管理，我知道這些數字在現場代表什麼。分析不是產出報表，是讓現場的人知道明天該改哪個動作。
